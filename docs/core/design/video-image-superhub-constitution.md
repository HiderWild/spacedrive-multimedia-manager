# 视频与图片超级管理中枢宪法

## 目的

本文档定义 Spacedrive 在视频与图片方向上的开发者总纲。

它不是需求清单，不是任务 backlog，也不是界面说明。它用于回答四个问题：

1. 我们到底在把 Spacedrive 改造成什么。
2. 什么能力应该优先进入核心产品。
3. 什么能力即使看起来有用，也不应该现在扩展。
4. 后续设计、实现、评审和取舍，应该用什么标准裁决。

本文档面向开发者。它是方向性文档，不是强约束规范，但它应当成为所有相关设计文档、任务拆解和 PR 评审的上位参照。

与本文档配套但职责不同的文档：

- `planning/media-suite/README.md` 和 `planning/media-suite/REQUIREMENTS.md` 负责能力拆分、epic 和任务化落地。
- `docs/core/design/` 下的其他设计文档负责某个子系统的具体方案。

## 愿景与产品定义

在这个方向上，Spacedrive 不再被定义为一个通用文件管理器，而被定义为一个面向巨量、拓扑复杂的视频与图片资产的本地优先超级管理中枢。

它的核心价值不是“能看见文件”，而是能在复杂目录、跨盘位、跨设备、跨标签体系、跨衍生文件链路中，稳定地完成发现、理解、筛选、批处理、组织、追踪与回退。

这里有三个关键词。

### 巨量

目标场景不是几千个素材，而是几十万到数百万级媒体对象，单库可覆盖多块本地盘、移动盘、NAS 映射目录和历史归档盘。

任何核心能力都不能默认小库场景。只在样例库里流畅，不算成立。

### 拓扑复杂

真实媒体库天然混乱，这不是异常输入，而是常态：

- 同一内容散落在不同盘符和目录层级
- 原片、代理、转码片、封面帧、缩略图、字幕和 sidecar 并存
- 同名不同内容、同内容不同路径、路径频繁迁移
- “按项目”“按年份”“按人物”“按来源”几套组织方式并存

系统不应该要求用户先把库整理干净，才能获得高级能力。产品价值恰恰在于帮助用户在复杂拓扑中建立秩序。

### 管理中枢

Spacedrive 在这里不是单点工具，而是统一的调度与组织中心。

旋转、转码、重命名、打标、归档、筛选、建立快捷入口、生成衍生物、触发批任务，这些动作都应围绕同一套内容身份、元数据、标签语义、任务系统和可回退操作模型来统一。

## 明确边界与非目标

### 明确边界

- 只聚焦视频与图片，音频、文档、压缩包和代码仓库不是当前主战场。
- 优先解决个人或小团队在本地与近线存储上的重度媒体管理问题，不先做企业审批流导向的 DAM。
- 优先解决高频管理动作和高成本组织动作，不先做轻量浏览器式图库。
- 优先建设可持续迭代的核心能力，不堆一批互不相连的工具按钮。

### 非目标

- 不以“支持所有文件类型的一致体验”为目标
- 不以“先做云端协作平台”为目标
- 不以“先做 AI 自动决策替代人工管理”为目标
- 不以“先覆盖专业剪辑或 NLE 全流程”为目标
- 不以“为每一种媒体工作流定制一个专门子系统”为目标

### 核心取舍

当通用文件管理能力与视频和图片的重度管理效率冲突时，优先后者。

这会直接影响功能抽象、索引策略、标签语义、批量操作中心和前端交互模型的取舍。

## 核心设计原则

### 1. 内容身份优先于路径身份

路径只是当前落点，不是稳定身份。系统的组织、去重、关联、批处理和历史追踪，应尽量建立在内容身份、文件身份、派生关系和稳定元数据之上，而不是只依赖路径。

### 2. 拓扑复杂性是常态，不是异常

多盘位、多层目录、跨卷迁移、历史归档、同内容多路径和派生链混杂，应被视为正常输入。系统必须适应它们，而不是回避它们。

### 3. 批量优先于单文件优先

单文件操作要顺手，但系统设计必须首先服务于批量场景。凡是现实中常常需要对几十、几百、几千个对象一起做的动作，都应优先考虑批量触发、批量预览、批量撤销、批量失败隔离和批量进度可观测。

### 4. 快速入口必须建立在强语义之上

快捷操作不应只是按钮集合。真正高价值的快捷操作，必须能绑定到明确对象集合和明确语义条件，例如某个标签子树、某个目录子树、某个派生状态、某个导入批次或某个问题集合。

### 5. 标签系统必须成为组织主轴之一

目录结构永远不够表达真实组织关系。目录主要表达存储位置，标签主要表达管理语义。这两者都重要，但在复杂媒体管理里，后者更能穿透拓扑复杂性。

### 6. 索引必须优先追求增量、稳定和低扰动

面对巨量媒体库，重新全量扫描不应是默认工作方式。索引的目标不是“每次都看完整个世界”，而是“尽快、尽准地找出发生了什么变化”。

### 7. 一切重操作都应进入统一任务模型

旋转、转码、提取缩略图、生成代理、批量改名、批量打标和批量归档，不应散落为不可追踪的即时动作。只要操作可能耗时、失败、需要恢复或影响大量对象，就应进入统一任务系统。

### 8. 人始终保留最终判断权

系统可以自动识别、自动建议、自动批处理，但不应默认替代用户的管理判断。删除、覆盖、重编码、移动原片、合并标签和覆盖元数据这类高风险动作，应优先提供可验证、可预览、可撤回的路径。

## 能力版图与功能拆解

本节是本文档的主体。它不是任务列表，而是从真实工作负载倒推出来的能力域。

### 1. 内容身份与拓扑感知

这是整个系统的地基。

必须具备的能力：

- 区分内容身份、文件身份和路径身份
- 识别同内容多路径、同路径历史迁移和同名异内容
- 建立原片、代理、转码片、封面帧、缩略图、字幕和 sidecar 元数据之间的派生关系
- 感知跨盘位、跨卷、跨目录层级的媒体分布拓扑
- 在文件移动、重命名和盘符变化后尽量保持关系连续性
- 识别孤立衍生物、缺失原片、失效代理和失配 sidecar

没有这层能力，系统只能遍历文件树，不能真正理解媒体库。

### 2. 高速索引与变化发现

这是巨量媒体库可用性的前提。

必须具备的能力：

- 支持初次全量建索引，但日常以增量发现为主
- Windows 上优先利用 NTFS 的稳定变化记录和文件身份能力
- 根据存储介质和文件系统能力选择不同索引策略，而不是全库一刀切
- 把元数据、媒体分析、缩略图和内容识别拆成分阶段执行
- 支持热区快速刷新，冷区延迟补全
- 对外接盘、历史归档盘和 NAS 映射目录采用不同扰动等级的策略
- 在高负载场景下，避免索引长期挤占转码、浏览和批处理资源

这一域的目标不是“扫得最全”，而是“在最小成本下最快知道哪里变了”。

### 3. 标签语义与分类组织

这是复杂媒体管理的核心组织语言之一。

必须具备的能力：

- 普通标签、层级标签和继承标签
- 标签同义、规范名和别名收敛
- 目录分类与标签分类并行存在，而不是互相替代
- 基于标签的动态集合、组合筛选和排除筛选
- 用标签表达主题、人物、项目、来源、用途、状态和质量问题
- 用工作状态标签表达 `待筛选`、`待精选`、`待转码`、`待归档`、`待复审` 这类流程状态
- 标签操作支持批量应用、批量覆盖、批量清理和冲突治理

目录主要描述素材放在哪里，标签主要描述素材在管理语义上是什么。

### 4. 批量操作与任务编排

这是“超级管理中枢”这个定义最直接的落点。

必须具备的能力：

- 批量旋转、批量转码、批量改名、批量移动、批量打标和批量归档
- 基于选择结果、筛选结果、目录子树、标签集合和问题集合触发批任务
- 操作前预览影响范围和策略差异
- 操作中显示进度、吞吐、失败项、重试项和资源占用
- 操作后保留可审计记录
- 尽量支持中断恢复、失败隔离和重复执行幂等
- 支持 CPU 或 GPU、质量或速度、原地覆盖或生成衍生物等策略选择
- 对高风险动作默认要求显式确认

如果一个批处理能力不能稳定处理上千对象，它就不能算核心能力成熟。

### 5. 快捷操作与工作流加速

这部分解决的是重度用户的日常效率，而不是功能炫技。

必须具备的能力：

- 可固定的快捷操作入口
- 可复用的批处理预设
- 绑定到明确查询条件的快速动作
- 键盘优先的高频管理流程
- 面向筛选、精选、归档、修正和交付的工作台式操作
- 临时集合、待处理队列、复审队列和可疑问题队列
- 一步进入 `未打标素材`、`重复候选`、`横竖屏异常`、`缺失代理`、`缺缩略图` 等专项视图

快捷操作必须绑定语义集合，不能只是一堆脱离上下文的按钮。

### 6. 浏览、筛选与人工整理

管理中枢不能只有后台能力，还要让人能快速做判断。

必须具备的能力：

- 面向巨量库的高密度浏览与连续翻阅
- 适合图片和视频的多种视图模式
- 面向人工筛选的快速保留、淘汰、标记和分组
- 基于标签、时间、路径、来源、格式、分辨率、时长、朝向和派生状态的联合筛选
- 快速发现低清、重复、旋转异常、损坏、缺缩略图和缺代理等问题素材
- 对连续拍摄、同项目素材和同来源导入批次的成组观察能力
- 让用户在浏览中直接进入管理动作，而不是在浏览和管理之间来回跳

目标不是做“好看的图库”，而是做“高判断密度的整理界面”。

### 7. 安全、可追溯与可回退

媒体管理成本高，误操作代价更高。

必须具备的能力：

- 对所有重要批处理保留操作历史
- 在可行处支持撤回、重试和回放
- 原片保护机制与高风险操作保护
- 对删除、覆盖、替换和衍生物清理提供清晰边界
- 记录谁触发了什么操作、影响了哪些对象、产生了哪些衍生结果
- 允许用户把“自动处理”和“仅建议”分开
- 对异常中断后留下的半成品、脏状态和孤儿文件提供恢复路径

如果系统不能让用户信任它，它就不能承担中枢角色。

### 8. 规则化自动化，但不取消人工主导

自动化应该增强管理能力，而不是接管管理权。

必须具备的能力：

- 基于条件的规则化批处理
- 可保存和复用的组织宏
- 对导入后、索引后和筛选后触发的自动流程
- 自动建议而非自动执行的模式
- 明确区分“可无损自动化”和“高风险需确认自动化”
- 为未来脚本化或 WASM 化能力保留边界
- 自动化结果回到统一任务与审计模型中

默认优先“人审后执行”，而不是“静默全自动”。

### 跨域机制

以下机制不是单独能力域，但应跨越多个能力域统一出现。

#### 工作状态标签

系统应明确区分“内容语义标签”和“流程状态标签”。前者描述素材是什么，后者描述素材下一步要做什么。两者混在一起会让整理、自动化和问题治理都变得混乱。

#### 问题集合视图

系统应把 `疑似重复`、`缺失代理`、`孤立 sidecar`、`旋转异常`、`元数据冲突`、`损坏候选` 这类问题聚合成可筛选、可复查、可批处理的集合，而不是只在日志或角落提示里暴露。

#### 导入批次与处理批次

系统应尽量保留“这批素材从哪里来、何时导入、后来被做了哪些处理”的批次语义。对大库用户来说，按批次回看、回滚、复审和归档，往往比按单文件操作更自然。

#### 衍生链治理

系统不只要能生成代理、缩略图和转码片，还应能知道它们何时过期、何时失配、何时可以回收、何时需要重建。衍生物不应长期处于无人治理状态。

## 关键技术主张

### 1. 不绕开 Spacedrive 核心底座另建媒体引擎

目标不是在 Spacedrive 旁边外挂一个媒体管理器，而是在现有 daemon、library、ops、jobs、indexing、VDFS、sidecar、tags 和 type generation 体系上，把视频和图片管理能力推到主角位置。

新增能力应尽量表现为：

- 新的 domain 概念
- 新的 query、action 和 job
- 对现有索引、标签、搜索和 sidecar 的增强
- 与前端类型生成链路一致的公开接口

### 2. 原片、衍生物和代理物必须进入统一关系模型

真正的管理对象不是单个文件，而是一个媒体对象及其衍生链。原片与转码片、代理文件、缩略图、关键帧、字幕和 sidecar 的关系，必须被系统显式建模，而不是只靠命名约定或前端局部逻辑。

### 3. Windows 上把 NTFS 能力视为高价值快路径

Windows 不是次要平台。NTFS 也不是普通文件系统之一。对 NTFS 的变化记录、文件身份和卷级能力利用，是核心性能战略的一部分。

同时，能力抽象优先于平台特判蔓延。产品可以为 NTFS 提供一流快路径，但代码结构仍应通过文件系统能力模型和策略路由来承载，而不是把 Windows 特判散落到各个功能角落。

### 4. 媒体分析必须分层

视频和图片的分析成本差异很大。系统应采用分层分析策略，而不是在发现文件后立刻把所有工作做完。

建议的层次：

- 轻量身份与基础元数据层
- 适合浏览的缩略图与预览层
- 适合筛选的媒体技术指标层
- 适合管理判断的问题检测层
- 适合深度处理的转码、代理、OCR 和场景理解等重层

首次可见性应优先于首次完整性，深成本任务应进入后台 jobs。

### 5. 搜索、筛选和批处理必须围绕同一选择模型

用户看到的集合、筛出来的集合、准备批量操作的集合、保存为快捷入口的集合，本质上应尽量落在同一套可表达、可序列化、可复用的选择模型上。

这样后续才能自然支持从查询直接发起批任务、把筛选条件保存为快捷操作、把问题视图转成待处理队列，以及把失败项重新收敛为可复查集合。

### 6. 所有高成本媒体能力都应优先设计为后台可恢复工作

批量转码、批量旋转、代理生成、缩略图补全、问题扫描、派生物校验和规则化批处理，都应默认按 job-first 思路设计。即时操作只适合轻量、高确定性的动作。

### 7. 类型与公开接口必须稳定

后端一旦引入公开媒体类型，就必须走现有 type generation 流程。前端必须消费生成类型，不自行重定义媒体核心结构。媒体状态、任务状态、派生关系和标签语义，以后端模型为准。

### 8. 先把“高频、重成本、强收益”的能力做深，再考虑花哨智能化

技术优先级应优先回答这些问题：

- 能不能更快发现变化
- 能不能更稳定处理百万级库
- 能不能更高效完成批量整理
- 能不能更可靠维护原片与衍生物关系
- 能不能让用户更少重复劳动

看起来聪明但不可验证、不可回退或只适合 demo 的能力，应后置。

## 开发决策准则

### 1. 优先选择能服务大库场景的方案

如果一个方案在小库里更简单，但在几十万到数百万媒体对象时会明显退化，那么它不应成为默认主路径。

### 2. 优先选择能被批量化的能力表达

如果一个需求既可以做成单点交互，也可以抽象成对对象集合的操作，优先后者。只有这样，它才能自然进入快捷操作、规则化自动化、任务编排和失败重试链路。

### 3. 优先选择可审计、可预览和可回退的实现

特别是影响原片、目录结构、衍生物链路和标签体系的能力。如果一个功能很强，但不能说明它改了什么、为何改、怎么撤回，它就不应轻易进入核心流。

### 4. 优先选择增量更新，而不是全量重算

只要有可能，应尽量从变化集中推导结果，而不是每次从整个媒体库重新计算。这条准则适用于索引、标签继承结果、问题检测、派生关系校验和快捷集合刷新。

### 5. 优先选择统一模型，而不是局部特化模型

如果一个新功能需要单独定义一套集合语义、任务状态、派生关系表达或标签解释方式，优先先看能否落入既有模型。局部最快的方案，常常会变成全局最贵的维护债。

### 6. 优先选择对用户心智一致的行为

同一种对象在浏览页、详情页、批处理面板和任务面板里，身份和状态解释应尽量一致。

### 7. 优先选择让人工整理更快的能力，而不是只让系统更聪明的能力

如果一个新能力能明显减少用户在筛选、判断、归类和批量修正上的时间，它的优先级通常更高。

### 8. 优先暴露问题，再自动修复问题

对重复候选、派生链缺失、旋转异常、元数据冲突和孤立 sidecar 这类问题，优先级顺序通常应是：先识别出来，再可筛选，再可批量处理，最后才考虑静默自动修复。

### 9. 平台优化可以激进，但产品行为要稳定

NTFS 快路径、不同卷策略和 GPU 转码选择，这些底层优化都可以因平台不同而不同，但从用户和上层调用看，行为语义应尽量稳定一致。

### 10. 任何新增复杂度都必须换来明确的管理收益

如果一个新子系统、新概念、新状态机或新数据库结构，不能清楚提升大库性能、批量效率、组织语义、可追溯性、用户判断效率或派生关系稳定性中的至少一项，就应谨慎引入。

### 11. 默认先做面向开发者可验证的能力

优先构建那些能明确写出输入、输出、边界条件和验收标准的能力，例如增量索引是否准确、标签继承是否正确、转码任务是否可恢复、失败项是否可重试。

### 12. 当通用性与视频和图片专用效率冲突时，优先专用效率

如果某个抽象足够通用，但会显著牺牲视频和图片重度场景里的组织效率、筛选效率、批量效率或索引效率，那么可以接受更偏媒体专用的设计。

## 里程碑式能力成熟度描述

我们不以“功能数量”衡量成熟度，而以“在真实复杂媒体库中能否长期稳定地管理和治理素材”衡量成熟度。

### M0：可见，但不可管理

系统已经能发现视频和图片，能展示基础信息，也能做初步预览。但这个阶段还不能被视为“超级管理中枢”成立。

典型特征：

- 能索引，能看，能搜一部分
- 对复杂拓扑理解有限
- 批量能力弱
- 标签语义不成体系
- 重操作缺乏任务化、审计和恢复能力

这个阶段只能证明“看见了媒体”，不能证明“管理得动媒体”。

### M1：可管理单批次，但还不够稳定

系统已经能对一批明确选中的视频和图片执行主要管理动作，并能看到任务进度和结果。这是进入“管理工具”门槛的阶段。

典型特征：

- 批量旋转、转码、打标和移动等核心动作可用
- 重操作进入统一任务系统
- 能对结果集合做稳定筛选
- 能识别部分派生关系
- 索引具备基本增量更新能力

但这个阶段通常仍存在几个问题：

- 大库性能不稳定
- 批处理失败恢复不足
- 拓扑变化后关系保持不牢
- 用户仍需大量人工弥补系统短板

### M2：可管理复杂媒体库

这是本文档的主目标层级。到这个层级，系统已经能在巨量、拓扑复杂的真实媒体库里稳定工作，而不是只在干净样例库里表现良好。

典型特征：

- 大库增量索引稳定，变化发现成本可控
- 标签、目录、筛选和快捷集合形成完整组织语言
- 原片、代理、转码片、缩略图和 sidecar 关系基本稳定
- 批量任务可恢复、可审计，失败隔离明确
- 浏览、筛选、人工整理与批处理之间切换顺畅
- 常见问题素材可被识别、聚合和批量处理
- 高价值快捷操作和规则化工作流开始可复用

如果没有达到这个层级，系统还不能被称为“视频与图片超级管理中枢”。

### M3：可作为长期中枢运行

这是更长期的上层目标。系统不仅能管理当前媒体库，还能成为用户长期积累、迁移、治理、复审和自动化的稳定核心。

典型特征：

- 跨设备、跨盘位和跨历史迁移后的关系仍然稳定
- 自动化规则可长期运行，且仍处于可审计边界内
- 问题检测、派生物治理和归档治理形成闭环
- 快捷工作流、任务历史、规则集和标签体系能持续演化
- 用户越来越少依赖外部零散工具完成核心媒体管理动作

## 用户故事附录

本附录用于压力测试系统是否足够强，不是需求真理来源，也不是开发顺序清单。

用户故事用于：

- 给设计原则提供真实语境
- 暴露功能之间的联动关系
- 防止把问题误解成单点工具需求
- 为后续 backlog 和具体设计文档提供高质量样本

用户故事不应直接绑死底层数据模型，也不应要求系统为每个故事生长一套独立子系统。

### A. 导入与建库类

#### 故事 A1：20TB 收藏库初次建库

- 角色：长期收藏视频和图片的个人用户
- 场景：手上有多块 NTFS 盘，目录结构多年演化，命名混乱，原片与转码片并存
- 目标：先把整库接入 Spacedrive，再逐步建立秩序，而不是先手工整理目录
- 当前痛点：现有工具要么索引太慢，要么只能按路径浏览，无法稳定识别重复与派生关系
- 系统必须支持的关键能力：
  - 增量优先的初次建库与后续刷新
  - 内容身份与路径身份分离
  - 派生链识别与问题集合视图
  - 标签化重组，而不是强迫立即搬运目录

#### 故事 A2：多设备素材导入后的批次整理

- 角色：同时使用相机、手机和无人机的内容创作者
- 场景：每周导入多批素材，每批都来自不同设备和拍摄场景
- 目标：按导入批次快速筛选、打标、生成代理，并把问题素材单独拉出来复审
- 当前痛点：导入后素材混在一起，后续回溯“这一批到底处理到哪一步”很困难
- 系统必须支持的关键能力：
  - 导入批次语义
  - 工作状态标签
  - 批量打标与批量转码
  - 问题集合和复审队列

#### 故事 A3：先接管，再慢慢重组目录

- 角色：已有多年历史目录但不想先大规模挪盘的整理者
- 场景：用户希望先让系统接管索引、筛选和标签，再逐步调整物理目录
- 目标：避免“先重构目录，后开始管理”的高风险路径
- 当前痛点：很多工具要求目录必须先干净，否则高级功能效果很差
- 系统必须支持的关键能力：
  - 复杂拓扑容忍
  - 标签作为主组织语言之一
  - 物理位置与管理语义解耦
  - 批量移动前的预览、模拟和回退

### B. 日常整理与筛选类

#### 故事 B1：从上万张照片中做精选

- 角色：高频拍摄的摄影重度用户
- 场景：一次活动导入上万张图片，需要快速淘汰废片、保留候选并打上主题标签
- 目标：在高密度浏览中快速做判断，不被界面切换拖慢
- 当前痛点：很多图库适合展示，不适合高强度筛选和工作状态流转
- 系统必须支持的关键能力：
  - 高密度浏览与连续翻阅
  - 键盘优先的筛选动作
  - 工作状态标签与快捷队列
  - 在浏览中直接批量管理

#### 故事 B2：视频素材快速分流到不同工作流

- 角色：短视频创作者
- 场景：需要把竖屏素材、横屏素材、可直发素材、待转码素材和待剪素材快速分开
- 目标：用标签和快捷操作把素材送入不同处理路径
- 当前痛点：路径结构无法同时表达拍摄来源、画幅、用途和处理状态
- 系统必须支持的关键能力：
  - 标签组合筛选
  - 工作状态标签
  - 可复用快捷操作
  - 从筛选结果直接发起批量任务

#### 故事 B3：围绕问题集合做日常治理

- 角色：长期维护大库的治理型用户
- 场景：每天想先看 `疑似重复`、`缺失代理`、`旋转异常`、`损坏候选` 这些集合
- 目标：像处理工单一样逐批消化库里的问题素材
- 当前痛点：异常通常散落在日志、失败任务和目录细节里，无法形成稳定工作台
- 系统必须支持的关键能力：
  - 问题集合视图
  - 问题集合到批任务的直连
  - 失败项复查与重试
  - 问题处理后的状态闭环

### C. 批量处理与派生治理类

#### 故事 C1：原片与代理链路长期共存

- 角色：后期工作者
- 场景：原片太大，日常浏览和初筛依赖代理文件，交付前再回到原片
- 目标：稳定维护原片、代理、转码片和预览图之间的关系
- 当前痛点：一旦目录调整或盘位变化，代理链很容易断裂
- 系统必须支持的关键能力：
  - 统一的派生关系模型
  - 代理生成与失效检测
  - 关系连续性维护
  - 针对缺失代理的治理队列

#### 故事 C2：批量修正历史方向错误

- 角色：持有大量历史视频和图片的老用户
- 场景：早年导入的素材中存在大量朝向错误、EXIF 混乱和预览不一致
- 目标：批量修正方向，同时保持元数据和色彩相关信息尽量正确
- 当前痛点：单文件修正太慢，批量修正又常常留下预览和元数据不一致的问题
- 系统必须支持的关键能力：
  - 批量旋转 job
  - 元数据与缩略图联动刷新
  - 高风险批处理预览
  - 批量失败隔离与重试

#### 故事 C3：批量转码并控制成本

- 角色：需要为浏览、分享和归档生成不同版本的用户
- 场景：同一批视频要同时生成轻量浏览版本、交付版本和流式播放版本
- 目标：让转码成为系统内的一等能力，而不是外部临时脚本
- 当前痛点：外部转码流程缺乏与库内对象、标签和任务历史的统一关系
- 系统必须支持的关键能力：
  - 可配置批量转码 job
  - CPU 与 GPU 路径选择
  - 原片与转码片关联
  - 按预设复用处理策略

### D. 长期维护与复杂拓扑类

#### 故事 D1：跨 NTFS 盘迁移后仍保持身份连续

- 角色：Windows 重度用户
- 场景：素材在多块 NTFS 盘之间迁移、扩容和重组是常态
- 目标：迁移后不丢失标签、派生关系和历史处理记录
- 当前痛点：很多工具把路径当主身份，一迁移就当成新文件
- 系统必须支持的关键能力：
  - NTFS 文件身份能力
  - 路径变化后的关系续接
  - 批量迁移的影响预估
  - 迁移后问题治理

#### 故事 D2：冷热分层存储下的长期维护

- 角色：同时使用本地 SSD、机械盘、移动盘和 NAS 的用户
- 场景：热素材常看，冷素材很少动，但都必须处于可追踪状态
- 目标：让系统按存储特性采用不同刷新和治理策略
- 当前痛点：全库同一策略不是太慢，就是太扰动冷数据区域
- 系统必须支持的关键能力：
  - 分区分层索引策略
  - 热区优先刷新
  - 冷区低扰动治理
  - 基于存储拓扑的任务调度

#### 故事 D3：规则化处理，但保留人工终审

- 角色：对重复劳动极度敏感的整理者
- 场景：希望导入后自动打上来源标签、自动补代理、自动把特定素材送入待复审队列
- 目标：减少重复劳动，但不接受黑盒自动清洗原片
- 当前痛点：自动化工具要么太弱，要么太猛，很难保持可控边界
- 系统必须支持的关键能力：
  - 规则化自动化
  - 自动建议与自动执行的分级
  - 统一任务与审计模型
  - 高风险动作需人工确认

#### 故事 D4：多年重复素材治理

- 角色：长期积累素材的归档维护者
- 场景：同一内容多年被重复备份、重复转存、重复导入，路径和命名都不一致
- 目标：先收敛出可信的重复候选，再分批做治理，而不是一次性暴力去重
- 当前痛点：大多数重复工具要么只看文件名，要么直接给出过度激进的删除建议
- 系统必须支持的关键能力：
  - 内容身份优先的重复候选识别
  - 可分层置信度的重复视图
  - 从问题集合进入批量治理
  - 原片保护与审计回退

## 结语

Spacedrive 在这个方向上的目标，不是再做一个“能看视频和图片的文件管理器”，而是成为一个能在真实复杂媒体库中长期稳定工作的管理中枢。

只要某项设计无法同时服务巨量规模、复杂拓扑、强批量、强语义和可回退这五个要求，它就还不够接近这份宪法。
